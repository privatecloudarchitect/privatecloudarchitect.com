Admin reference · organization and project access

Access rides two planes, and that decides how you vend a project

Grant a tenant by intent, not by the biggest role that clears the ticket. Access is decided on two planes with different controls, and the developer services plane answers to only one of them. That single fact sets how many projects you vend, and the vend itself is three API calls with no console step. This reference is the model, the tier ladder, the isolation ceiling, and the runbook, in that order.

Verdict

Grant by intent; and when self-service on the services plane must stay own-only, give each trust boundary its own project.

A tenant who only deploys from the catalog and manages their own work is Organization User plus Project User. A tenant who needs the developer services portal needs Project Advanced User, which sees the whole project and holds no per-user ownership on the workload plane. So services self-service and own-only coexist only inside a project that holds one trust boundary, and the three-call vend in section 04 makes a project per boundary the affordable default rather than a last resort.

01

Two roles set access on two planes, and the services portal rides only one

org role, then project role, then the plane it decides

Effective access is decided by two roles applied in order, and the project role is the center of gravity. The organization role opens the portal and, for one role, bypasses everything below it. The project role grants consumption and decides which of two surfaces a tenant holds.

Organization User defers to the project role. Organization Administrator sees every deployment in every project, so self-service users are Organization User, never Administrator.

Two planes

Deployment plane

catalog items, deployments, Day-2 actions

Visibility comes from the two roles; actions come from Day-2 action policies. A Project User consumes here with own-only visibility, and this is where governed self-service lives for anyone who does not need kubectl.

Workload plane · the services portal

Virtual Machine Service, Kubernetes, volumes

The Kubernetes API of each namespace, reached at the namespace endpoint. Access is the project role tier alone; Day-2 policies do not reach here. This is the plane the services tiles operate, and it begins at Advanced User.

PatternNamespace creation needs the catalogs, not a broad grant. Project Administrator carries the create-namespace right, but the new-namespace form reads org-gated catalogs (namespace classes, regions, storage classes). Deliver them with a narrow custom organization role that adds only those read rights, or publish Namespace Self-Service to the project. Neither grants org-wide visibility.
03

The workload plane holds no per-user ownership, so the project is the isolation unit

why the project count follows from trust boundaries

The scar first: inside one namespace, two Advanced Users are the same Kubernetes identity, so each can act on every object regardless of who created it. That is not a tuning problem to solve with a smaller grant. It is a ceiling, and it decides your project count.

Shared project, many tenants

the anti-pattern for own-only services

Every Advanced User sees and can act on every namespace object in the project. A custom organization role does not open a smaller door, and a hand-authored namespace binding cannot admit a non-member, so there is no boundary below the project to carve.

One project per trust boundary

the recommended unit for services self-service

The owner is Advanced User in a project that holds only their own work, so project-wide equals own-only, and other projects are invisible. This is the vend in section 04, run per tenant.

Design ruleA tenant who must self-serve the services portal and must not reach another tenant's resources gets their own project. The project count is a function of the trust boundaries, not the user count: a team that trusts itself is one project; ten engineers who must not touch each other's services are ten projects, each a three-call vend.
ReadingWhere the requirement is only deployment-plane own-only and no services portal, a single shared project works: keep tenants on edit, whose own-only visibility scopes any granted Day-2 actions to their own deployments. That path simply does not carry the services tiles.
From model to operation
04

Vend a project and its first namespace in three API calls

no console step; the third call is the one that used to fight back

Creating and deleting projects is an organization-level right no project role carries, so the vend is a provider-administrator operation. It is also fully scriptable. Three calls against the Cloud Consumption Interface, under one interactive session token, take a tenant from nothing to a Ready namespace. Values in angle brackets are estate specifics: read the region, VPC, and service engine group from a namespace that already works.

Mint an interactive session token. The interactive login carries the rights the vend needs; an automation token does not. Read the token from the response header and reuse it for all three calls.POST /cloudapi/1.0.0/sessions Authorization: Basic base64("admin@Org:password") # read X-VMWARE-VCLOUD-ACCESS-TOKEN as the bearer
Create the project. One POST creates the cluster-scoped project object; it carries a name and a description.POST /cci/kubernetes/apis/project.cci.vmware.com/v1alpha2/projects { "kind": "Project", "metadata": { "name": "checkout-team" }, "spec": { "description": "Vended project for checkout-team." } }
Bind the owner and the operators. One ProjectRoleBinding per subject. Users bind by bare name, groups by name with a trailing marker. Choose the owner's role by tier: edit_adv for a services owner, admin to also manage namespaces.POST .../authorization.cci.vmware.com/v1alpha1/namespaces/checkout-team/projectrolebindings { "kind": "ProjectRoleBinding", "metadata": { "name": "cci:user:alice", "namespace": "checkout-team" }, "roleRef": { "apiGroup": "authorization.cci.vmware.com", "kind": "ProjectRole", "name": "edit_adv" }, "subjects": [ { "kind": "User", "name": "alice" } ] } # repeat for the operators group: name "cci:group:platform-admins", # roleRef admin, subject kind Group name "platform-admins@"
Create the first namespace. Name it by generateName, not a fixed name, and give it the service engine group. These two fields are what the old opaque error was asking for; the region and VPC resolve against the organization. Then poll to Ready.POST .../infrastructure.cci.vmware.com/v1alpha3/namespaces/checkout-team/supervisornamespaces { "kind": "SupervisorNamespace", "metadata": { "generateName": "checkout-prod-us-west-1-", "namespace": "checkout-team" }, "spec": { "className": "large", "regionName": "<region>", "vpcName": "<vpc>", "segName": "<service-engine-group>", "classConfigOverrides": { "zones": [ { "name": "<zone>", "cpuLimit": "2000M", "memoryLimit": "4000Mi" } ] } } } # poll GET .../supervisornamespaces/<derived-name> until status.phase is Created
Verify before believing it. Read the namespace back to status.phase: Created, and confirm the owner can reach the services portal in their new namespace. A vend that has not admitted a namespace is not done.
Watch point

The two fields the fresh-project error was really asking for

A brand-new project can meet a complete namespace spec with an opaque validation error, and the reasonable read is that the project lacks a region. It does not. A fixed metadata.name is rejected in favor of generateName, and on a region whose load balancing is registered through NSX the create requires the service engine group by name. Supply both and a fresh project hosts its first namespace by API, no console step, on any organization that already carries a region.

At scaleLoop the three calls over an onboarding list. Each vend is seconds of API work, so a project per trust boundary is cheap. A governed variant wraps the vend behind a catalog request and an approval, so tenants ask for a project and an operator approves the vend.

How to read the chips

Outcome chips encode desirability, not HTTP status: a denial that serves isolation is good, an over-grant is caution even when the API said yes.
