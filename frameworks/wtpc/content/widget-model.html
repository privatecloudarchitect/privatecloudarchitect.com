The two units of a tuned cloud
This framework governs two different things with two different units, so no object is ever judged by a policy that is not its own. Read this once. It is the model every scorecard below renders.
Two objects, two owners
The workload
A VM, tagged by what it is → its posture
Environment, function, service level. The posture is the workload's contract: per-VM performance and protection, scored against the workload's own envelope. A dev VM never counts against a prod breach.
prod-latency-critical-db holds its memory and tolerates almost no contention. test-dev-traditional packs freely.
The hardware
A host or cluster, by what it provides → its tier
The tier is the hardware's promise: how hard it may be packed (the overcommit ceiling) and the cluster-wide floors it guarantees. It is judged against what it provides, not against the strictest guest it happens to run.
dedicated packs at 1.0× (no overcommit). density packs at 4.0×.
A host's capacity envelope is a property of its tier, what it provides, never of the strictest workload it happens to host. Conflating the two is a category error: it makes the hardware inherit a workload's hardware requirement, the collapse that produced the mixed-service-level scoring anomalies. vROps allows one effective policy per object; partitioning objects across the two units (VM to posture, host and cluster to tier) satisfies that rule by construction, so the two families never compete for the same object.
What an envelope is
An envelope is the acceptable-state schema for one signal, per posture: a target, a warn edge, and a breach line. Scoring is relative to the posture, never a universal ideal. The same metric carries opposite envelopes across postures. Below, one signal, memory overcommit, on a shared 0 to 4.5× scale.
prod-latency-critical-db strict
target 1.0× · warn 1.1× · breach 1.25×
test-dev-traditional permissive
target 2.0× · warn 3.0× · breach 4.0×
Same signal, opposite envelopes. The strict posture's entire tolerance ends near 1.25×, where the permissive posture is still comfortably inside its band at 3×. Envelope Position normalizes every signal to observed ÷ breach, so 1.0 is the breach line for all of them. That is what lets one heatmap ruler color every posture: the same color is the same distance from breach, whatever the raw numbers.
Which unit owns which axis
Not every axis can be judged per VM. The split follows the physics of the axis.
Axis family How it composes Owned by
Cluster-atomic
HA admission control, N+k host redundancy, anti-affinity, EVC		 A cluster holds exactly one of each. The strictest resident wins, unconditionally. The tier, as guarantees. A shortfall is a placement-fit finding, not a silent downgrade.
Partitionable
CPU ready and co-stop, memory contention, balloon, swap		 Isolate per VM with reservations and shares, then score each VM against its own posture. The posture, per VM. A dev VM never counts against a prod breach.
Aggregate ratio
memory and CPU overcommit		 One ratio over the whole host: provisioned summed ÷ physical, reservation-blind. It cannot be expressed per VM, and one policy per object forbids splitting it. The tier's ceiling. This axis is where the original strictest-workload rule was replaced.
What the framework does not do
It does not make hardware inherit the strictest workload's hardware requirement. A latency-critical VM landing on a high-overcommit host is a fit finding on the VM, not a red score on the host. The workload is misplaced; the hardware is doing exactly what its tier promised. The fix is placement, not a policy edit. Overcommit is a physical property the tier owns; performance is a per-VM property the posture owns.
Hardware follows the workload, slowly
Hardware still follows the workload, but only as a lagging observability inference. A newly tagged VM pulls its host and cluster into the posture's membership within about one re-resolution cycle. A departing VM does not free the hardware promptly: a dwell window and an empty-group guard hold the membership so a live migration cannot thrash a tier. Hardware acquires a workload quickly and releases it slowly, by design.
And the framework observes and advises. It never places. DRS, HA admission control, and the deployment pipeline place; the scorecards read the result and tell you where it drifted from the envelope.
One word, two meanings. A posture's tier input (production, staging, test-dev) is the workload's environment class. A hardware tier (dedicated, performance, standard, density) is what the metal provides. This page is about the second. Every threshold a scorecard shows is stamped from the posture and tier catalogs, never a house number.
